# Python 全量规范整改计划

## 目标与范围

继续上一轮全部 312 个项目 Python 文件的审核，修复已知规范问题并复核适用强制项。应用、知识导入、脚本、测试及公共入口全部纳入；新增项目 Python 文件自动纳入最终清单。沿用 Python >=3.9、Pydantic v2 及现有框架，不安装新依赖，不重置既有改动，不提交或推送，不运行真实数据库写入或迁移。

## 整改顺序与责任

1. 固化当前源码指纹和 100 passed / 2 skipped 的上一轮测试基线。父代理先完成全范围 Black 格式整理，再交付两个互不重叠的写入范围，防止格式化与行为修改相互覆盖。
2. 接口/数据子代理负责 `gustobot/application/services`、`gustobot/infrastructure`、`gustobot/interfaces`、`gustobot/config`、`gustobot/crawler`、`kb_ingest`、`scripts` 和既有 tests。修复实际类型契约、失败/资源/异步问题，处理其范围内 Flake8。对 MySQL 导入原始 WHERE 表达式先查真实调用方，使用现有解析器或参数化结构消除 SQL 拼接风险，保留可表达的筛选能力；变更之前建立边界回归。
3. Agent/RAG 子代理负责整个 `gustobot/application/agents`、`gustobot/application/prompts` 及新建的本轮 RAG 回归文件。逐项修复实际类型/数据形状、必需字段、None/零值、可变默认值、异常和资源契约，处理其范围内 Flake8。修改行为前先添加或运行能暴露问题的测试。
4. 父代理负责项目工具配置、根入口、公共包标记、跨范围复核和最终报告。类型检查明确覆盖所有第一方文件；对缺少类型声明或使用当前目标版本以外语法的第三方包限定导入分析边界，不忽略第一方类型错误、不关闭既有检查选项。格式工具仅记录确有 Black 协议冲突的例外。
5. 两个子代理均重新核对所负责的全部文件与适用强制规则；删除已确认无用和重复实现，再修正剩余逻辑。不得用 `Any`、`cast`、`type: ignore`、`noqa`、吞异常、弱化测试或空值兜底使工具表面通过；实际第三方动态边界若必须适配须有具体协议和说明。
6. 运行全量 Black、Flake8、Ruff F/E9、Mypy、编译/Python 3.9 AST、Bandit 与安全离线测试。诊断失败继续处理；推荐规则如有真实框架/业务例外，逐项解释保留理由。真实服务及真实 Python 3.9 运行缺口如实记录，不将未验证表述为成功。
7. 重新生成完整逐文件记录、SHA256、修改清单、覆盖率及最终验证；逐条核对残留问题、规则适用性和保留依据，完成独立复核后交付。

## 验收

- 每个项目 Python 文件均有当前审核记录；无遗漏、重复或陈旧指纹。
- 本仓全部第一方代码的 Black、配置后的 Flake8、Ruff F/E9 与 Mypy 通过，配置差异有明确技术原因。
- 现有安全测试和新增行为回归通过；不产生已知功能退化。
- 强制项无已知未修复违反；推荐项的具体例外与运行验证边界单独列出。容器监听等合法运行配置不通过无依据更改来消除扫描提示。

## 整合期间的有界接管

- 父代理接管 `infrastructure/core/database.py` 和 `infrastructure/persistence/`，将 ORM 字段改为 SQLAlchemy 2 的真实 `Mapped` 契约；对照只读 metadata 快照保留字段类型、可空性、主外键，建立实际 SQLite 关联/JSON 往返回归。
- 在改动前分别复现提交失败未回滚、回滚/关闭错误覆盖原操作错误、activity 方法没有更新持久时间戳；由事务拥有者回滚，原始错误继续传播。
- 应用关闭先以回归复现未使用服务被创建、单个清理失败阻止其余资源释放，以及取消/协作式挂起的清理缺口，再增加逐拥有者清理和有限屏蔽；线程中阻塞代码仍受供应商自身 I/O 超时约束。
- 父代理接管 Studio、Python 3.9 兼容、RAG 组件和脚本四个旧回归文件的类型/格式修正；启用 `check_untyped_defs`，连同无注解函数体一起验证。
- 按实际用途整理已使用依赖的声明与测试工具分组，不安装新库或升级框架。动态打包元数据从既有 requirements 文件读取。
- 交叉复核后，将脚本、HTTP 流和 Agent 节点实际重复的拥有者清理统一到 `infrastructure/core/resources.py` 的 `close_on_exit`；覆盖部分初始化、关闭双失败、取消和协作式超时。清理工具自身也纳入逐文件审核，原有业务错误元数据继续由外层负责。
