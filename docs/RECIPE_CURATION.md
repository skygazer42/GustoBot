# 菜谱逐条查证与补全

每批以主数据的物理行序冻结 ID、整条原始记录和 SHA-256。行号用于人工核对，修订按稳定 ID 应用。审查前报告保留；修订结果另记，不能把原问题报告改成全部通过。

1. 读取原始资料，逐项核对用料、每阶段用量、份数、设备、操作、时间、温度、图片和保存条件。
2. 原文缺失或相互矛盾时，继续查原作者页面、生产商说明、官方指南和其他可靠作者完整配方。记录实际读到的全文；摘要、验证码和打不开的页面分别登记，不能当已核实全文。
3. 优先补全实际内容。采用其他作者版本时统一整套量表与流程、明确署名，不能把不同配方的数字随意拼接。编辑选材、缩放实例与作者原文区分记录。
4. 用量表与步骤相互核对：每项原料有使用去向，操作中新增原料进入量表，可选项与互斥做法都明确；原版图片与修订流程不同则解除错误步骤关联并说明。
5. 热量等营养信息先查匹配食品状态的官方成分表或确切产品标签，再按可食部与明确用量计算。保留克重换算、来源、公式和范围；没有实际吸油量、弃汤量、品牌或可食部重量时，补具体原料资料及已知用量小计，继续说明具体缺口，不能把未知当零或把小计称整菜热量。
6. 营养素作用引用官方说明。食材含蛋白质、膳食纤维等事实不能推导为治疗效果，也不自动构成高蛋白、高钙或低热量声称。
7. 每项修订绑定原审查问题和实际证据。全部分片完成、复核后再启用注册表；重建时验证前置摘要、问题覆盖和来源闭环，同步所有子集及导入文件。
8. 验证仅目标 ID 改变、原文身份保留、图片关联有效、营养计算可复现，以及既有导入契约与本体约束。文献复核与实际试做分别记录。

修订文件位于 `data/recipes/corrections/`，官方原料资料及精确匹配配置位于 `data/recipes/nutrition/`。原始字段仅用于血缘核对；使用修订菜谱时应读取当前 `ingredients`、`steps`、`tips`、`durations` 等字段，不把审查前原文当作另一套同时执行的步骤。

营养文件按修订批次登记在 `data/recipes/nutrition/registry.json`。后续批次在独立目录补充成分表与匹配配置，不能原地改动上一批已发布资料，避免连带改变旧菜谱的数值和证据摘要。自定义单套营养资料时须同时提供 `--nutrition-profiles` 与 `--nutrition-matches`；默认构建使用分批注册表。

默认命令：

```powershell
python scripts/build_recipe_dataset.py --offline --download-images
python scripts/build_recipe_dataset.py --verify
```

上游原文许可不自动覆盖本轮引入的其他作者文字或图片。补充内容单独记录许可待核状态，并从开放许可子集中排除；开发快照不意味着已取得公开再分发授权。
