# 数据来源与血缘

本文说明本地知识数据的来源、用途和可追溯性。原始资料、菜谱快照和核验记录集中在 `data/`，随本地备份迁移。代码仓库通过 Git 忽略该目录。

- **数据来源**：内容最初来自哪个文件、网页或数据集。
- **检索后端**：本次回答从 Neo4j 事实图或 Milvus 原文索引中的哪一个取回。

当前响应分别返回 `source` 和 `backend`。MySQL 记录来源版本、作业和会话，不因为存储了元数据而成为内容的原始出处。

## 按菜品关联的文章

首批资料覆盖番茄炒蛋、宫保鸡丁、麻婆豆腐、鱼香肉丝、回锅肉、红烧肉和蛋炒饭。番茄炒蛋包含百科背景与维基教科书工序两篇，其余主题各一篇。来源、许可与导入方法记录在本机 `data/kb/dishes/README.md`，修订和校验值记录在同目录的 `manifest.json`。2026-11-21 已在本机 8001 预览服务发布全部 8 篇，并回读核对 33 个文本分块及对应概念事实。分块数取决于该环境的配置。

文章作为现有文档知识库的一部分，按菜品实体关联，不为每道菜创建单独的数据库或向量集合。图谱和文本使用同一来源 ID、完整 Markdown 正文、固定修订 URL 和正文版本。文章导入只登记有逐字证据的菜品概念，不凭百科内容制造配方、用量或工序关系。

已选择菜谱时，回答同时准备完整的当前菜谱、已确认的相关概念事实与已发布文章片段，再进行一次综合生成。当前菜谱的 ID 和版本必须通过会话校验；跨名称背景关联另核对 `catalog_recipe_refs` 中的 ID 与版本，不按显示名称猜测某个图谱配方。尚无准确图谱配方映射时，只使用概念事实补充背景。普通事实问答则可沿正式本体关系找到关联概念文章。计数、排序、排除条件等仍需本体执行依据，文章不能冒充全量事实。

回答会区分当前配方与文章中的其他说法，并返回实际取回的来源。用户明确限定只看某类资料时遵守限制；某支路无结果与检索故障分别处理。当前没有把生成答案自动写回知识库的机制，新增知识仍需来源与审核。

这些资料是首批文章覆盖，不代表整个菜谱目录都已有配套文章。番茄炒蛋目前仅关联已存图谱，不误绑公开目录中的番茄蛋汤或挂面；红烧肉属于两种做法的共享背景，《炒飯》属于蛋炒饭的上位背景。

菜谱与图像许可分开保存。TheMealDB 未声明具体许可证的图片标为 `unknown`；供应商的 CC 确认标志不被推断为 CC BY 4.0。完整合并集没有统一的无限制商用许可；`recipes.open-license.jsonl` 仅表示上游仓库的开放许可声明，不能代替独立权利核验。

数据字段包括稳定 ID、语言、原始用量、有序步骤、原始做法、现有菜系、国家、视频、图像角色及本地校验结果、逐条来源与版本。缺失信息先继续查找原作者、官方和可靠作者资料补齐，不凭空编造；27 条旧库编号不规则的记录标记 `step_numbering_needs_review`，并保留完整原文。未修订的 HowToCook 计算公式和多阶段用量保留原文；本轮明确的单份编辑实例与缩放公式分开记录。

准备好本地 OpenKG 基线 `data/recipe.json` 后，运行 `python scripts/build_recipe_dataset.py --download-images` 构建快照。已有完整缓存时可用 `--offline --download-images`。运行 `python scripts/build_recipe_dataset.py --verify` 检查 JSONL、摘要、图片解码、子集和导入文件的一致性。本地的内容修订和营养资料随 `data/recipes/` 一并迁移。

`expansion.import.json` 只包含新增来源，采用现有 `name` / `record` 契约。图片、许可等元数据可随来源原文保留，但当前业务查询和前端不会自动展示这些新图片；实际入库及展示需要显式接入。

### 内容准确性审查进度

2026-11-21 按完整 `recipes.jsonl` 的物理行序，对第 1–50 条进行了逐字段内容审查，报告位于本机 `data/recipes/audits/2026-11-21-rows-0001-0050/README.md`。每条均对照固定提交原文并检索下厨房等独立资料，分别记录网站拦截、搜索摘要和实际读到的全文。56 个图片引用均已目视查看。

本批 45 条发现需要修正的内容或解析问题，5 条证据不足，没有将任何整条菜谱标为完全准确。问题包括伪食材、量表与操作矛盾、互斥做法串联、图片与步骤错绑、温标换算错误，以及没有计算依据的热量和健康断言。不同作者配方差异仅按变体记录。原文一致和文件完整性验证均不代表真实烹饪准确性。

审查前冻结的行号、菜谱 ID、原始记录、Markdown、来源链接与逐字段建议保留不变。随后第 1–50 条按固定 ID 应用实际内容修订，记录在本机 `data/recipes/corrections/rows-0001-0050/`。248 项原审查问题逐项绑定修改字段和证据。采用其他作者配方时整套替换并署名，原图与新版不一致时标为原版本参考，原始来源身份和原文不改写。

第二批第 51–100 条的审查记录 `data/recipes/audits/2026-11-21-rows-0051-0100/README.md` 包含 1,994 项检查与 296 项原问题，实际修改见本机 `data/recipes/corrections/rows-0051-0100/README.md`。35 个本地图引用已目视查看，第 66 条原外链另行访问返回 HTTP 404，保留未确认图像内容的真实状态。第二批仅改动这 50 个 ID，目前累计修订前 100 条。

营养补充的说明位于本机 `data/recipes/nutrition/README.md`。数据使用 USDA FoodData Central SR Legacy、日本文部科学省食品成分表及 FDA 等官方资料，保留食品生熟、干湿、可食部口径与份量换算。每条修订菜谱的 `nutrition` 提供原料事实、已知用量小计和来源；部分小计不称为整菜热量，也不编造吸油率、成菜克重或品牌营养值。没有确切产品标签时，官方同类产品示例另列 `reference_foods`，不计入当前配方小计。

本轮新增作者资料的补充内容许可与上游原文分开判断，`curation.supplemental_content_license_status` 为待核的条目不会进入开放许可子集。已保存文献依据不等于通过实际烹饪验证，也未自动入库。

后续批次沿用[逐条查证与补全流程](RECIPE_CURATION.md)，先查其他资料补全内容，再校验与重建，不能仅更换问题标签。

## 默认检索链路

所有内置领域使用同一套本体约束服务。Neo4j 返回事实及其来源和引文；Milvus 返回已发布来源版本中的原文分块，按领域、本体版本和 embedding 模型过滤。关联回答可用实体 ID 把图中对象与原文对齐。LightRAG 和 pgvector 不参与当前主链。

当前知识响应中的来源对象示例：

```json
{
  "backend": "milvus",
  "source": "data.txt",
  "document_id": "<稳定分块 ID>"
}
```

`backend` 表示本次真正命中的检索后端；`source` 表示被索引内容的来源文件。回答正文不会再由模型自行猜测或生成数据库来源标签。

## 替换演示数据

- 原文：通过 `scripts/import_knowledge.py documents --path <文件>`，或受管上传后显式调用 `/api/v1/knowledge/documents`。
- 菜谱事实：通过 `scripts/import_knowledge.py recipes --path <JSON>`，或 `scripts/import_recipes.py --file <JSON>` 调用同一入库 API。
- 文档事实：先 `/api/v1/ontology/extract` 取得候选，审核后通过 `/api/v1/ontology/facts` 直接写图。
- `scripts/recipe_kg_to_csv.py` 只做离线 CSV 导出；旧文件与卷不会被自动转换为当前索引。

重新入库时建议在每条记录的 metadata 中保留 `source`、`url`、`author`、`license` 和采集日期，避免再次丢失血缘信息。
