# 现有图分支合并与轻量本体约束

日期：2026-11-15。状态：根据用户澄清后的代码核查与后续方案，未实施生产代码合并、路由切换或数据迁移。

## 当前方向

保留现有图分支及 LightRAG 的检索与回答职责，先合并重复接入与资源管理，再补充领域语义约束。此前 `2026-11-15-minimal-rag-core.md` 中“普通 RAG 默认、LightRAG 默认关闭”是备选路线，不作为本次实施前提。减重不要求把现有图问答改成普通文档问答。

参考用户提供 PDF 第五章，重点阅读 PDF 第 281—284、296、312—324、326、329、331 页。与本项目相关的方法是：显式定义领域概念和关系，将约束落实到抽取、遍历和证据校验，并保留来源。书中方法与示例不能作为本项目已实现或生产效果的证据；轻量领域约束也不等同于完整 OWL 推理或 SHACL 实现。

Text2Cypher 的严格属性/枚举/范围校验目前只在非 LLM validation 模式启用。默认路径的只读检查、EXPLAIN、方向修正及 LLM 核查不能被描述为全量确定性本体校验。

## 第一阶段：直接合并重复的 LightRAG 接入

1. 保留 `gustobot/application/services/lightrag_service.py` 为唯一第三方封装，集中模型、embedding、工作目录、初始化、查询、入库与关闭。沿用已有索引维度推断，保留现有数据。
2. 删除 `components/customer_tools/node.py` 中重复的完整 `LightRAGAPI`，节点只负责任务输入及 `cyphers/errors/records.result/steps` 状态转换。第一阶段继续使用现有 `aquery` 答案语义，不同时切换到证据生成新流程。
3. 显式迁移脚本与测试调用方：旧 API 返回查询字典及 `error` 计数，公共服务返回文本/生成器及 `failed/errors` 模型，不能靠类名别名掩盖契约差异。
4. Agent 和 HTTP 共用应用级实例；首次初始化需并发保护，部分失败清理不得重复获取同一把锁；单次请求只关闭本次生成器，应用退出关闭共享运行时。CLI 自有实例自有关闭。文件索引多进程写入边界需单独约束，进程内锁不能解决它。
5. 不改现有路由、KB scope 或默认图职责，不新增通用 ProviderFactory，不因合并强制升级 LightRAG、重建索引或迁移数据库。可延迟加载图依赖，避免无关模块导入触发图初始化。

必要回归：现有图路由与状态输出、HTTP/SSE 协议、入库部分成功计数、并发首次初始化、取消与失败清理，以及 CLI 资源所有权。

LightRAG 当前使用默认 NetworkX/JSON/NanoVectorDB，Neo4j 是独立的结构化菜谱图；合并 Python 封装不等于融合图数据。即使后续将 LightRAG 存储换为 Neo4j，也仍需实体和关系映射，不能认为用了同一数据库就自动共享领域模型。

## 第二阶段：补最小的领域语义约束

以已有菜谱契约和固定关系为基础，整理一处实际维护的领域定义：实体类型、稳定标识、允许的关系及起终点类型、用量单位、步骤顺序和来源要求。优先使用现有 Python/Pydantic 与 Neo4j，不预建本体平台或引入新推理框架。

抽取时模型生成候选事实，代码校验实体类型、关系起终点、数据类型与来源；关系类型允许并不代表该关系事实为真，仍需原文证据与必要的质量复核。遇到业务未知值应显式表达未知，不能伪造用量或关系补齐模型。

查询时根据问题明确本次允许的关系路径、深度、结果量与证据要求，由查询代码实施。Pydantic 负责数据契约，Cypher/检索代码负责实际遍历边界。只有需要标准交换、类层次推理或标准约束验证时，再分别评估 RDF/OWL/SHACL；不将普通 Python 校验命名为 SHACL。

LightRAG 1.4.9.8 的 `entity_types` 提示可引导类别，但不是强制本体校验。其默认关系输出使用关键词和描述，不能直接等同于有明确方向、起终点类型的菜谱关系。仅修改 prompt，或在 `aquery_data()` 结果上事后过滤，均不能证明内部检索只遍历了允许的边。强约束关系问答优先复用可控的 Neo4j 查询；LightRAG 继续负责文档图检索和综合信息。

## 第三阶段：按需求贯通证据

如果要将多个工具的事实合成一个有统一引用的答案，再使用当前版本已有的 `aquery_data()` 获取结构化证据，显式处理实体、关系、片段与原文引用，并接入真正的回答生成步骤。不能把原始证据当答案，也不应先调用 `aquery()` 生成再无条件生成第二遍。独立 HTTP 的既有答案契约需保留。

验收使用实际业务问题：菜谱别名锚定到同一实体；只沿本次允许的食材/步骤关系查询；未知用量不编造；文档观点与结构化事实可区分；每条关系证据能定位原文或记录；缺证据与服务故障不混为正常空结果。只有固定案例和真实服务验证后，才报告质量、延迟或成本改善。
